\subsection{Dataset}

% We use 100 maintenance cases for training and testing with \tool{}. The cases
% comprise 24 core tasks and 76 derived tasks across 11 groups (G1--G11). Each
% case pairs a starting repository with a maintenance request, typically for a
% local functional change. The agent must infer which temporal obligations apply
% from documentation, code, or tests and often satisfy several at once, including
% constraints on event order, data binding, and lifecycle permissions.
% Executable checks assess whether the patch implements the requested change and
% preserves those obligations under controlled event schedules. The cases cover
% seven programming languages (JavaScript, TypeScript, Python, Java, PHP, Ruby,
% and Go) and five framework or library families. Implementations range from
% single-module programs to multi-module applications and upstream library
% repositories.

In this study, we constructed a dataset contains 100 maintenance cases, comprising 24 core tasks and
76 derived tasks across 11 scenario and family groups. Each case includes a starting
repository, a maintenance request, and executable checks. Requests typically
describe local functional changes while leaving temporal obligations partly
or wholly unstated. A single change often involves multiple obligations on
event order, data binding, or lifecycle permissions, supported by repository
documentation, code, or tests. Executable checks assess the requested behaviour
and temporal-contract preservation under controlled event schedules. The cases
span seven programming languages (JavaScript, TypeScript, Python, Java, PHP,
Ruby, and Go) and five framework or library families, with implementations
ranging from single-module programs to multi-module applications and upstream
library repositories.



\subsection{Implementation Details}

% Experiments ran on Ubuntu 20.04.6 with Docker 28.1.1.
% We used \texttt{gpt-6.1-sol} and \texttt{gpt-5.6-sol} with medium
% reasoning effort and priority service.
% Table~\ref{tab:tempoevo-main-evaluation} lists the Codex CLI versions
% for the main runs. Each training-set replay allowed up to three repair Actions. Each
% test run used one Action, followed by final scoring by the Gold
% evaluator. Each Action was capped at 24 LLM requests and 600 seconds.
% Evaluation used frozen experience libraries. The 20-entry subset
% was sampled with seed \texttt{20261118}. Cases with invalid executions
% were reported separately and excluded from pass-rate denominators.

Experiments ran on Ubuntu 20.04.6 with Docker 28.1.1.
We used \texttt{gpt-6.1-sol} and \texttt{gpt-5.6-sol} with medium
reasoning effort and priority service.
Table~\ref{tab:tempoevo-main-evaluation} lists the Codex CLI versions
for the main runs. Each training-set replay allowed up to three repair
Actions. Each test run used one Action, followed by final scoring by
the Gold evaluator. Each Action was capped at 24 LLM requests and
600 seconds. A senior software engineer (Q.Y. C.) with 16 years of
development experience reviewed candidate repair experience before
approval for reuse. Evaluation used frozen experience libraries.


\subsection{Main Evaluation}

Experience-guided repair ranks highest in all five settings
(Table~\ref{tab:tempoevo-main-evaluation}). Auto-Contract Only improves over
latent repair in three, but lowers DeepSeek's pass rate.
Both experience-enabled DeepSeek variants pass 18/30 tasks.

\subsection{Experience Library Size}

Figure~\ref{fig:tempoevo-memory-size} compares library-size ablations on
30 test tasks. GPT-5.6 Sol rises from 34.9\% without experience to 83.7\%
with 40 entries and 83.6\% with 61. DeepSeek Flash yields 60.5\% with
20 entries, 56.9\% with 40, and 60.0\% with 58, versus 19.9\% without
experience. The 20- and 40-entry sets are nested random subsets of each
model's frozen library.
