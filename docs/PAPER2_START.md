# Paper 2 起步说明：工具如何帮助编码 Agent

## 暂定研究对象

Paper 2 研究的是“源码派生证据如何改变编码 Agent 的检查和修改行为”，不是再次评估 `temporal-contract-bench` 本身。当前工具把同一次静态扫描拆成 B/C/D 三层，并另外提供不含项目线索的开放式审查条件，因此可以区分“被指到哪里”“看见什么结构事实”和“收到怎样的解释”这几类帮助。

## 首要问题

1. B 仅提供位置时，是否减少搜索成本，同时造成过早收敛或漏查未列位置？
2. C 增加结构事实后，是否改善调用关系和跨作用域状态的恢复，而不明显增加越界修改？
3. D 增加启发式解释后，何时帮助形成正确假设，何时因规则不完整或误命中形成锚定？
4. E 与 D 的差异，是“通用搜索策略”与“局部项目线索”的差异，还是主要由输入长度与位置选择造成？
5. G 是否能让 Agent 同时获得开放搜索和局部线索，并降低只围绕 D 命中位置修补的倾向？

## 最小研究单位

每次实验应冻结并保留：

- 候选源码树和原始任务输入的摘要；
- 工具实现、位置选择和每层报告的摘要与实际字节；
- 模型、推理等级、超时、条件、重复编号和随机运行顺序；
- 最终提示词、Agent 轨迹、补丁、测试/评分结果、超时与资源使用；
- 失败类型、遗漏义务、越界修改和新增测试，而不只保留 PASS。

## 起步顺序

1. 先稳定 `0.4.0` 的分析 schema、B/C/D 生成与校验路径。
2. 从已知开发案例做机制探索，明确 D 成功与失败的可观察模式；这些结果不得冒充未见验证。
3. 在规则开发之外冻结案例选择、假设、排除标准和主要指标，再运行独立验证。
4. 将分析器改动与实验批次绑定；实现或规则变化后新建批次，不续跑旧计划。
5. Paper 1 完成前保持实验边界：不把这里的新实现隐式替换 Paper 1 的既有工具输入。

## 当前非目标

- 不把规则命中解释为缺陷、难度或成功概率。
- 不把 D 当作完整仓库检查清单或自动修复器。
- 不从 Paper 1 的既有结果反复挑选“最有利”的案例来验证 Paper 2 假设。
- 不在此阶段迁移 Paper 1 的 Web、运行器、案例库、Oracle、评分器或历史档案。
