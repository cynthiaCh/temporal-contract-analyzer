# Temporal contract skill: ownership, completion, and effects

Purpose: complete the original maintenance task. Use this skill where timing or ownership can affect its behavior. The task and project evidence determine the contract.

S1 Applicability. Check whether work can finish after an initiating access or consumer changes, callbacks can run during setup or cleanup, or one result produces effects with different validity rules. If none applies, briefly record why and continue the maintenance task.

S2 Establish evidence. Read the entry point, producer or decoder, completion path, ownership transitions, cancellation path, and affected consumers. Inspect adjacent implementations for supported patterns, not automatic specifications. Record source locations for consequential facts. Separate task requirements, observed behavior, hypotheses, and unavailable evidence. Names, familiar patterns, and passing local checks do not establish a contract.

S3 Define identities and effects. Track the resource, access, operation or attempt, and accepted result wherever the source distinguishes them. For each effect, including waiting state, scheduled work, delivery, records, and visible state, state which identity must remain valid when it occurs. Determine what cancellation actually stops. Do not assume every effect shares one stale-result rule.

S4 Define state meaning across the full interval. Before changing a status flag, establish from its consumers and transitions whether it represents an in-flight request, an unfinished overall operation, or something else. Trace its value at start, after an interim result, while later work is scheduled, after completion, and after close or disposal. Check that an interim result neither triggers a final effect nor clears an indication that must persist until completion. If evidence does not settle the meaning, mark it unknown and avoid presenting an assumption as fact.

S5 Trace handoffs and reentry. Follow the order in which listeners attach, work starts, handles become available, ownership is published, and cleanup runs. At calls into external or user code, consider synchronous reentry where the API permits it. Check ownership before and after calls when later steps depend on the original owner. Ensure an old operation cannot publish a handle or effect over a replacement. Check immediate results against the intended consumers and each effect’s contract.

S6 Compare concrete event orders. Using project-supported APIs, cover ordinary completion; interim result followed by later completion; completion after close, switch, or disposal; reuse of a resource under a new access; and replacement or retry within an access. Compare normal and reversed settlement order when possible. For scheduled work, compare pending-to-ready behavior with cancellation, reopening, replacement, disposal, and callback execution during scheduling where supported. Observe state immediately after each meaningful transition, especially while work is pending. Assert each affected effect and ownership state separately. Derive ordering from source-supported identity or arrival sequence; do not invent a payload schema.

S7 Preserve established behavior. Keep public interfaces, unrelated consumers, streaming, records, diagnostics, cleanup, and adjacent behavior consistent with the task. Distinguish an access ending from an attempt ending. Resolve whether closing a view cancels background work, and whether stored and visible effects share a lifetime, from task and source evidence. Otherwise mark these questions unknown.

S8 Repair and verify. Implement the smallest supported change that completes the maintenance task. Run relevant available checks and inspect their actual output. Add focused checks for meaningful untested orders and, when applicable, a boundary or reentry path. A local harness proves only the paths it drives; a syntax check proves syntax, not behavior. Treat missing dependencies, failed commands, and unrun checks according to what they establish. If a check fails, revise and rerun the relevant check. Finish with the maintenance result, observed verification, and explicit remaining uncertainty. A contract discussion alone is not completion.
