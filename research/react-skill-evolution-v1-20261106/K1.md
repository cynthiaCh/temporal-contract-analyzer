# Temporal contract skill: result ownership and effect validity

Purpose: complete the original maintenance task. This skill aids repair; it is not a second task, a prose-only substitute, or a business specification. Apply only what the task and visible project evidence support.

S1 Applicability. Look for work that can finish after the initiating access, operation, or consumer changes, or a callback that can change ownership while another call runs. Look for multiple effects, such as a stored record and a current display. If absent, state why this skill does not apply and continue the maintenance task.

S2 Source evidence. Read the entry, actual producer, decoder or dependency, completion callback, ownership transition and cancellation path, plus each relevant effect consumer. Cite source locations. Separate task requirements, source facts, hypotheses, and missing evidence. Establish whether an initial value is emitted synchronously and which consumers require it. Do not infer a dependency guarantee from its name or add plausible input formats or behavior.

S3 Check relations. Identify resource, access or visit, physical operation or attempt, and accepted value or work wherever code distinguishes them. Trace where each identity is captured, retired, and compared. Determine whether cancellation prevents new input, cancels scheduled work, aborts work already started, or only hides a consumer. For each effect, write its acceptance and publication conditions separately. In particular, decide from evidence whether accepted work still owes a durable effect after its view closes, and whether a later result may update the current view. Do not copy one validity guard across effects by default.

S4 Compare concrete orders. Trace ordinary completion; completion after close or switch; same-resource reuse; and replacement or retry when present. At each external call that the source permits to invoke a callback synchronously, trace the call stack through callback reentry and the outer call's return: note whether ownership changed, whether a cleanup handle arrived late, and whether the outer continuation can still publish or schedule. Check both a callback before the external call returns and a callback after it returns when the dependency permits both. For ordered full results, compare arrival order with reversed completion order; observe durable and visible effects separately without inventing a frame schema. If a required order cannot be driven with visible APIs, label it unverified rather than assuming the ordinary order covers it.

S5 Non-applicability and unknowns. Background obligations, rollback, permission withdrawal, or dependencies that truly suppress completion can change the answer. Find visible evidence or leave the point unresolved. Do not impose persistence after cancellation or access-based cancellation on every project. Preserve other consumers of shared helpers and original public interfaces.

S6 Repair and verify. Implement the smallest supported maintenance change, or explain with evidence why no change is needed or why the task remains incomplete. Run relevant visible checks after the final edit and inspect actual output. Test ordinary use and the applicable orders from S4, including independent effects, reuse, cleanup, and adjacent behavior. State which checks use real integration and which use substitutes, and name uncovered orders and failed or unrun checks. Revise when results warrant it. A contract discussion, syntax check, or successful self-written smoke check alone does not establish completion of the original repair.
