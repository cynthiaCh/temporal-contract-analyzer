# 固定实现的边界与运行期观察

本轮控制器不是完整语义状态机。同步hooks确实在真实工具后运行，可以补充上下文、拒绝有限次修改并请求同一session继续；它不代替Codex选择行动、解释业务、实现补丁或设计测试。语义正确仍由可信行为评分和研究侧实际轨迹/补丁复核判定。

正式运行后观察到的覆盖边界，保持冻结实现，不按早期结果改代码：

- 读取分类是命令/路径启发式；`rg --files`的目录列表也可能被计为source observation并使collect转inspect。这证明真实工具输出已获得，不证明相应源码内容已读。最终机制复核必须引用实际cat/nl/sed输出，不能用该计数声称查证充分。
- 真实Bash的PostToolUse在本机可只提供stdout，不带结构化退出码。控制器记录exit_code=null；合成测试中的结构化退出码路径不能被冒称已覆盖本机所有失败工具。事后分析采用CLI command_execution的真实退出码。验证记录还可由实际stdout中的passed/AssertionError识别，但无输出的成功检查可能未被识别。
- 引用检查只核对候选路径/行数与曾观察到的文件；事件顺序只核对记录存在，不验证其业务含义。仅有检查记录、补丁和自写测试也可能可信评分失败。
- PreToolUse修改分类有shell启发式盲区，至多拒绝2次；Stop至多继续2次，达到上限可以带明确未满足状态结束。无论机械完成门是否通过，整体任务是否完成仍以实际维护交付和可信评分区分。
- /controller.py只读挂载，/control为独立状态/观察目录，不交付给隐藏评分；现有工具sandbox不授权/control写入。此设计不宣称抵御恶意Agent规避或所有命令路径，未把控制器当安全沙箱。
- Hook观察、追加上下文和Stop续行都可能改变预算分配和注意；A/B差异不等于单一推理机制的因果贡献。底层模型请求次数和所有用量单列，正式CLI会话数不能冒充实际只有同样数量的网络推理请求。

实际开发证据：download/K0 的 CLI events 33、45、47、59 都有真实 Node 检查通过输出（`PASS ...`），但控制器最终 `validations=[]`；对应 hook 日志 Stop 两次 continue-same-session，随后 allow-stop-with-unresolved-limit。原因可由固定分类器与原始输入核对：本机只提供stdout，缺少退出码，分类器仅识别小写化后的passed/AssertionError，未识别PASS。这是验证观察的漏报，造成重复记录与重复执行；不能把这些续行全部计为解决新失败的有效查证。可信行为评分该次PASS，机械门未满足与语义结果应分开。
