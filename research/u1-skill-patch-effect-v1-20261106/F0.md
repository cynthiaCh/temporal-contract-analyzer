# Temporal contract skill: result ownership and effect validity

Purpose: complete the original maintenance task using the project’s visible contract. This skill guides investigation, repair, and verification; it does not add requirements.

S1 Applicability. Use this skill when work may finish after its initiating access, operation, or consumer changes; when callbacks can change ownership during an active call; or when one result has multiple effects. Otherwise, note the source evidence for non-applicability and continue the maintenance task.

S2 Establish evidence. Inspect the entry point, producer or decoder, call and return sequence, completion path, ownership transitions, cancellation or release path, and every relevant effect consumer. Inspect shared helpers and adjacent consumers before changing their behavior. Record task requirements, source facts with locations, hypotheses, and unavailable evidence separately. Do not infer guarantees from names or plausible formats.

S3 Map identities and effects. Identify distinct resource, access, physical operation, and accepted-result identities where the code supports them. Trace when each is created, published, replaced, retired, and checked. For every effect, determine its own validity rule from the task and source: a historical record, current display, notification, or cleanup may have different owners. Determine whether cancellation prevents new input, stops work already started, suppresses an effect, or invokes reentrant callbacks. Do not apply one guard to all effects without evidence.

S4 Trace event order. Write a short timeline for each relevant boundary: ordinary completion; completion after close or switch; reuse of the same resource; replacement or retry; and synchronous callback reentry. Include startup and teardown ordering, especially callbacks fired before an operation returns or while a listener is released. At each step, track the current owner, operation identity, listener state, pending work, and effects already committed. Check whether reentry can replace ownership before the original call resumes.

S5 Compare ordered results. If complete results can settle out of order, distinguish arrival order from completion order using only the visible producer contract. Determine which order governs each effect. Check ordinary and reversed completion, including results begun before a lifecycle transition. Avoid inventing a result schema or suppressing history merely to protect a current view.

S6 Preserve behavior. Keep the original task’s public interfaces and adjacent behavior unless authorized evidence requires a change. Check whether a shared source has consumers with different startup or delivery rules. Treat background obligations, rollback, permission withdrawal, and dependencies that truly suppress completion as project-specific facts to establish, not universal rules. Leave unresolved questions explicit when evidence is unavailable.

S7 Repair and verify. Make the smallest supported maintenance change, or explain with evidence why no change is needed or why work remains incomplete. Before treating a fix as complete, run relevant available checks and targeted scenarios for the timelines above. Assert each affected effect separately, including what persists and what reaches the current consumer. Drive reentry through the actual visible callback path and inspect state and effects after the outer call returns. Exercise adjacent consumers and ordinary use where the change can affect them. Inspect real check output, revise on failure, and report failed or unrun checks. A passing local scenario establishes only the orders it drove; it does not establish whole-task success.
