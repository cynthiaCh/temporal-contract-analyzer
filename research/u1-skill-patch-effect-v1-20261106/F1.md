# Temporal contract skill: input admission, result ownership, and effect validity

Purpose: complete the original maintenance task. Use this skill to inspect timing and ownership only where the task and visible project evidence warrant it. It is not a separate specification or a prose-only deliverable.

S1 Applicability. Look for synchronous emission during startup, work that completes after its initiating access or operation changes, and callbacks that can change ownership while another call is running. Look for distinct effects, such as durable history and a current view. If none apply, note the source-backed reason and continue the maintenance task.

S2 Gather evidence. Inspect the entry point, producer or decoder, subscription and startup order, completion path, ownership transitions, cancellation and release path, and every affected consumer. Inspect relevant callers of shared helpers. Cite source locations when explaining conclusions. Separate task requirements, source facts, observations, hypotheses, and unavailable evidence. Do not infer a dependency guarantee from a name or invent an input format.

S3 Trace admission and completion separately. For each input, identify when it can enter the consumer, when it becomes accepted work, and when its result settles. Follow the resource, access or visit, physical operation or attempt, and accepted-result identity wherever the code distinguishes them. Determine from source whether cancellation stops future input, cancels accepted work, suppresses completion, or only changes a consumer's visibility. Check listener removal and ownership handoff during synchronous, reentrant callbacks. A result accepted before a transition may have different obligations from an input emitted after the transition; establish those obligations for this project rather than assuming either should be recorded.

S4 Specify each effect's contract. For each history, audit, notification, queue, display, or other affected effect, identify the identity and validity condition it needs at delivery time. Check whether a result belongs to a prior access, a replaced attempt within the same access, or the current attempt. Keep durable effects and current presentation distinct. For ordered full results, determine from source which order defines freshness, then compare ordinary and reversed completion. Do not infer order from decoded values or invent a frame schema.

S5 Compare concrete event orders. With controllable visible APIs, exercise ordinary startup and streaming; completion before and after close, switch, or retry; a fresh input emitted from an old source after handoff; same-resource reuse; and synchronous callback reentry where supported. Observe admission, accepted work, durable effects, and visible effects separately. Include combined orders where one callback triggers a lifecycle transition during startup or cleanup. Check the exact boundary around release: whether future inputs can still reach an old listener, and whether already accepted work still settles as required.

S6 Preserve behavior. Keep public interfaces and unrelated consumers of shared helpers intact. Check queue and notice behavior, cleanup, navigation, retry, and diagnostic or other adjacent consumers to the extent the original task and source make them relevant. Background obligations, rollback, permission withdrawal, and dependencies that truly suppress completion can change the contract; require visible evidence or leave the point unresolved. Do not impose one cancellation or persistence policy on every project.

S7 Repair and verify. Implement the smallest source-supported maintenance change, or explain with evidence why no change is needed or why the task remains incomplete. Run relevant candidate-visible checks and inspect actual output. Make checks distinguish new input after release from delayed completion of previously accepted work, and observe both durable and current effects. Test ordinary and reversed result order, lifecycle boundaries, reuse, reentry, and adjacent behavior where applicable. Revise if a check exposes a mismatch. A successful local harness establishes only the paths it drives; a prose contract or smoke check alone does not complete a repair. Report failed, unavailable, and unrun checks explicitly.
