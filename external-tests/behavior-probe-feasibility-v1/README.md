# 自动组合时序探针：最小可行性验证

本轮验证的是一个受限能力：**人工提供 API 绑定与行为要求后，工具能否用通用模板自动组合并运行有用的时序场景。**没有为各项目向生成器输入测试函数，没有修改静态分析规则，也没有调用 LLM 生成测试。

结果：这条流程可以运行，并复现了已有五组上游问题的修复差异。**这只能说明模板组合这一步可行，不能证明工具可以自行理解任意代码、发现任意时序问题或具有论文新颖性。**本批复用已经看过的开发案例，不能再称为独立留出评估。

## 实际运行

- 独立原型：[probe.py](../../tools/temporal-behavior-probe/probe.py) 与 [runner.mjs](../../tools/temporal-behavior-probe/runner.mjs)，版本 0.1.0。
- 最终结果：[run-02/summary.json](run-02/summary.json)。10 个配置（5 组历史修复、5 个通过所选检查的对照配置），7 个实现；普通/strict once 是同一实现的不同入口。
- 自动组合 **57 个场景**，两侧各跑一次，共 **114 次隔离执行**；0 次 inconclusive。
- 普通顺序基线 11 个场景，增强场景 46 个。基线均未违反所声明的要求；增强场景在问题版本发现 9 个违约场景，其中 8 个在对应修复版本消失，1 个仍存在。场景相关，不是 9 个独立 bug。
- 5 个通过所选检查的对照配置均无违约，也没有同版本前后运行差异。这不是通用误报率。
- 新增 9 项专项测试通过。保留静态分析器 0.6.9 和此前原始输入，未安装新依赖。

## 五组已知问题

| 实现 | 自动生成的场景 | 问题版 → 修复版 | 与普通基线的差别 |
| --- | --- | --- | --- |
| eventemitter3 | 一位 once 监听在回调中立即再次派发 | 调用 2 次 → 1 次 | 普通顺序派发两次都表现为只调用一次 |
| mitt | 首个监听移除自身/下一个监听；组合 2/3 个监听 | 漏交付 → 全部交付 | 不移除监听时两版均正常 |
| 历史 memoize-one | 成功参数、失败参数、同失败参数重试；以及先失败再重试 | 返回旧值/undefined → 抛出异常 | 重复成功参数时两版均正确缓存 |
| p-memoize | 不等待首个调用，立即再次调用，随后释放延迟结果 | 求值 2 次 → 1 次 | 等待首个调用完成后再调用，两版均有缓存 |
| inflight | 完成回调抛错，再注册同一个键 | 无法开始 → 可以开始 | 不抛错的完成与重新注册两版均正常 |

每个项目目录的 `plan.json` 只包含三类信息：模块位置/环境、API 绑定和布尔行为要求。`generated-scenarios.json` 是生成器输出的操作描述。没有把旧 witness.test.mjs、修复 diff 或 bug 标签传给生成器；外层开发评估知道这些案例的历史背景。

## 一个额外组合场景

通用 emitter 模板同时尝试 1/2 个 once 监听。两个 once 监听 A/B 同时存在时，让 A 在第一次执行中再次派发事件：

| 版本 | A 执行次数 | B 执行次数 |
| --- | ---: | ---: |
| 历史问题版 | 2 | 2 |
| 历史修复版 | 1 | 2 |
| 另行最小脚本中的 Node 原生参考 | 1 | 1 |

因此历史补丁解决了单监听路径，但不能据此宣称全部重入场景都修复。生成报告把这个场景保留为 `violates_on_both`，没有计入八个“该场景已改善”的结果。

这不是针对项目新增的生成规则；同一模板原先就枚举了两个监听。发现结果后，另写 [confirm-multi-once.cjs](confirm-multi-once.cjs) 进行最小复核，其输出保存为 [confirmation.json](run-02/confirmation.json)。该复核脚本不参与生成或评估打分，作者仍是同一执行者，不能当作独立外部审查。此处只谈所固定的历史版本，未测试或宣称当前发布版本存在此问题，也未获维护者确认。

## 为什么现代缓存没有被误判

先前静态工具会提示现代 memoize-one 在计算后才写缓存。这里显式提供的要求是：成功重复调用可缓存；失败参数不能返回旧成功值；异常不能破坏之前的成功缓存。

“同步重入只准求值一次”没有被强加给普通 memoization。该版本六个生成场景均未违反所声明要求。重入执行次数仍作为观察保留，不能因执行两次就自动判错。行为要求的选择由人根据文档确认，这是重要的人工输入。

## 自动和人工各负责什么

**人工输入**：API 形状、导出/方法名字、构造方式、有效的简单输入域，以及文档或上游记录支持的行为要求。Flow 类型擦除与运行依赖是既有共享准备步骤，不是项目专用的测试函数。

**工具自动完成**：枚举重复调用/一次重入/异常重试/重叠调用/监听移除的通用场景，建立带计数的回调，运行前后模块，采集返回与抛错、回调次数和源码调用帧，按显式要求评估并输出变化。

这是有限操作语法上的模板实例化与参数组合。没有自动发现 API，没有自动从自然语言提取契约，也没有从任意程序合成全新的测试逻辑。三个 API profile 是人工设计的，不能把“项目无需手写测试”扩大为“工具无需人工测试知识”。

## 复现

运行整个开发批次需使用新输出目录：

```sh
python3 -B external-tests/behavior-probe-feasibility-v1/run.py \
  --output external-tests/behavior-probe-feasibility-v1/run-03
```

重放一个生成场景：

```sh
python3 tools/temporal-behavior-probe/probe.py \
  external-tests/behavior-probe-feasibility-v1/run-02/eventemitter3/plan.json \
  --scenario once-reentry-2 --output /tmp/new-once-replay.json
```

`<subject>` 调用帧对应 plan 中该侧 root。模块与真实依赖在临时目录运行；这不是安全沙箱。Node v24.21.0、现有 Flow 类型擦除与原生 TS 擦除沿用上一批的环境。

`run-01` 是初次完整运行；`run-02` 修正 macOS 源调用帧中 `/private` 的路径别名前缀，场景和契约未变。每批保存实际引擎源码，运行时检查引擎没有变化。超时、准备/加载失败均标为 inconclusive，不当作已违反契约或安全。
