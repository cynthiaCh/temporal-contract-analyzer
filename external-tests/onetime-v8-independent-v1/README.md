## 复现了什么

上游在 L17 判断 `function_` 仍存在，L18 调用它，L19 才将它置为 `undefined`。如果用户函数在 L18 执行期间立即再次调用包装入口，内层仍能看到这个函数，因而再次执行。

简化的见证（完整检查见 `witness.test.mjs`）：

```js
let calls = 0;
const wrapped = onetime(() => {
  calls++;
  if (calls === 1) wrapped(); // 只重入一次，避免无限递归
});
wrapped();
// calls === 2
```

自写的检查把“成功的同步调用中，重入不得重复执行回调”作为待验证期望。这一解释与上游 README 的单次调用描述相符，但 README 没有单独约定同步重入语义。该行为尚未获得维护者的缺陷确认，本次没有发 issue/PR。

5 项控制检查分别验证：普通重复调用、后续调用的 throw 选项、this 保留、首次同步抛错后重试、微任务中的再次调用。两项失败分别为默认配置下同步重入两次执行，以及 throw 配置下同步重入未拒绝。微任务重入只执行一次，说明此处的时序区别确实影响行为。

## 为什么 0.6.2 没报告

这不只是展示筛选隐藏了提示：原始 `findings` 也是空的。核对现有 `publication.py` 可见三处覆盖限制：

1. 入口状态和外部函数恰好都是参数绑定 `function_`；同一绑定在调用后被重新赋值，`parameter_call()` 对存在任何可见写入的参数会保守放弃识别。
2. 外部调用位于 `if (function_)` 的条件分支中；当前状态发布分析不把这种条件调用纳入可报告链。
3. 使状态失效的写入也在分支中；当前分析不推理该分支内的调用/写入顺序及分支条件成立的事实。

改进需要保留调用点之前的绑定身份，并分析受 guard 约束的分支内路径，而不是直接放开所有条件分支。还有一个约束：上游明确有“首次抛错后允许重试”的测试；简单提前清空 `function_` 会改变此行为，不能据此自动给出修复。

- 选择时看过其测试与 README；自写探针的期望是研究者设定，不是独立 ground truth。
- 未改动工具、候选实现或依赖实现；不增加工具依赖、不安装 npm 包。MIT 许可随源码保存。
- 实际运行使用原始 `mimic-function` 5.0.1，提交 `e451d0af761bed2cde0b9bc252dc6a2dfeb35844`，通过临时目录的正常 Node 包解析加载，没有 mock 或依赖替换。
- 所有下载文件及来源记录均由 `SOURCE_HASHES.json` 绑定；运行脚本和见证代码摘要另存于结果。只对本例记录漏报，不计算总体 precision/recall。
