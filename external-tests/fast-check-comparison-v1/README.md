# 与直接使用 fast-check 的开发对照

问题：当前 Temporal Behavior Probe 是否比直接使用测试框架，更容易获得、定位和理解修改前后的时序反例？

**目前不能证明。**本次给 fast-check 相同的 API/行为要求，并编写独立、可复用的通用属性模型后，它也获得了五组已知问题的反例，能够缩减、重放，并用同一最小反例验证修复前后的变化。附加回调计数与调用帧后，它能给出与原型相近的触发位置信息。没有测量开发者理解正确率、任务时间或模型编写时间。

## 对照方式

- 输入复用 behavior-probe-feasibility-v1/run-02 的 10 个计划：7 个实现，5 组真实历史修复，以及 5 个行为对照配置。案例已用于开发，不是新的留出测试。
- 固定 fast-check **4.10.2**、pure-rand **8.0.0**。它们仅作为本实验的发布包副本保存，校验 registry 完整性；没有修改工具依赖或执行 npm install。
- 采用 17、42、2027 三个 seed，每个启用属性最多 100 个成功尝试，保留正常缩减。失败会提前结束；缩减和重放另有执行。因此 numRuns 不是完整函数调用次数。
- [baseline.mjs](baseline.mjs) 独立实现三类 API 的属性模型，未导入原型的场景生成器、执行器或契约判断代码。它读取相同 API/契约配置，不读取修复 diff、旧测试函数或预期场景名称。
- 监听数量 1–4、调用/失败次数等有限参数由 fast-check 生成。范围与原型固定 57 场景不完全相同；不能用总耗时或测试数推断效率优劣。
- 每个属性尝试重新加载目标模块并创建新的被测对象。CJS 清理目标根目录下的模块缓存，ESM 使用独立 URL；每个版本/seed 在单独进程执行。依赖和源码准备与原型相同，执行隔离成本不同，未做速度对比。
- 先搜索两侧各自的反例，再将缩减后的修改前反例重放到修改后。不能因为修改后仍有另一个失败场景，就忽略已有改善。

流程与解释限制在运行前写入 [PROTOCOL.md](PROTOCOL.md)。先用晚发布错误、提前守卫正确实现和 Node 原生 EventEmitter 做属性模型校准，结果位于 smoke-01。

## 五组问题的结果

| 问题 | 原型 | 直接 fast-check 属性模型 |
| --- | --- | --- |
| eventemitter3：once 重入 | 获得单监听反例，并保留双监听残留问题 | 三个 seed 均获得反例；before 缩减为 1 个监听＋重入，after 另发现 2 个监听＋重入的残留问题 |
| mitt：派发时移除监听 | 获得漏交付反例 | 三个 seed 均获得并重放缩减反例 |
| 历史 memoize-one：异常后错误命中缓存 | 获得异常重试反例 | 三个 seed 均获得并重放缩减反例 |
| p-memoize：未等待的相同调用重复求值 | 获得重叠调用反例 | 三个 seed 均获得并重放缩减反例 |
| inflight：回调抛错后不能重启同键请求 | 获得失败清理反例 | 三个 seed 均获得并重放反例 |

五个行为对照配置均未产生契约反例。它们不是一般意义上的无缺陷项目，结果也不是通用误报率。

完整结果：[run-02/summary.json](run-02/summary.json)。共记录 10,818 个初始搜索 numRuns、25 次成功缩减步骤、18 个失败属性记录。18 个是前后版本/seed 相关记录，**不是 18 个 bug**。18 个失败记录均重放匹配，并包含附加的被测代码调用帧。五组问题在三个 seed 下均获得目标反例，其修改前反例重放到对应修复版均通过；历史 eventemitter3 修复版仍有更大的残留反例。

## 具体例子

fast-check 对历史 eventemitter3 的 once_delivery 属性得到：

```json
{"listeners": 1, "reenter": true, "emissions": 1}
```

问题版回调执行两次，修复版使用同一个输入只执行一次。独立搜索修复版又得到：

```json
{"listeners": 2, "reenter": true, "emissions": 1}
```

此时第二个 once 监听仍执行两次，与原型的额外组合场景一致。相应 seed/path、缩减次数、断言和源调用帧均保留。此处是固定历史版本，不涉及当前发布版本或维护者确认。

## 获得、定位、理解分别能说什么

**获得反例**：两边都能做到，未观察到原型独有的检测能力。fast-check 还具备本原型未实现的自动缩减。这不说明任意随机测试能开箱即用找到问题；本次明确为它提供了与原型同类的时序知识和断言。

**定位**：原型默认采集回调调用帧；fast-check 的通用模型中添加计数和调用帧后，也能采集相同类型的触发位置。原生框架报告与附加观测分别保留，未故意隐藏框架能提供的信息。两者定位的都是触发调用处，均未自动证明“哪一行状态更新是根因”或给出已验证补丁。

**理解**：原型自动呈现同一场景的前后状态与契约变化；直接框架可通过配对重放和报告代码得到类似材料，本实验也实现了这个对照。没有真实使用者或理解任务的时间/正确率数据，不能从报告样式或作者主观感受推出“更容易理解”。

## 配置成本不能这样比较

不能只计算原型的 JSON 行数，再把 fast-check 的全部通用属性代码算成每个项目都要重写的工作。

本次 fast-check 的通用模型写好后，**同样直接复用原有 10 份 API/契约计划**，没有为各项目编写专用测试函数。两边都有一次性的领域模型设计成本，也都有项目的绑定、契约确认与运行环境准备成本。

代码库存分别保留：原型 probe.py 为 205 行、runner.mjs 为 116 行；本实验 baseline.mjs 为 189 行、准备/运行脚本 run.py 为 132 行。这些代码角色和语言不完全相同，行数不是人力、易用性、复杂度或维护成本测量，不能据此宣称谁更省力。它们只用于避免隐去任一侧的公共实现成本。

## 对工具定位的含义

当前原型更适合视为**回调领域模型与前后行为报告的封装**，不宜主张新的测试生成或执行能力。已有测试框架可以作为底层；是否仍有足够额外价值，需要验证跨新实现的适配工作量、配置错误率，以及开发者完成具体理解任务的表现。

本实验没有证明“原型更好”，也没有证明领域封装毫无价值；它排除了一个较弱论据：不能因为普通顺序测试漏掉问题，就推断现有测试框架没有能力发现它。

## 复现与文件

```sh
python3 -B external-tests/fast-check-comparison-v1/run.py \
  --output external-tests/fast-check-comparison-v1/run-03
```

需在项目根目录运行，输出目录必须尚不存在。依赖已经保存，无需网络或 npm 安装。默认 Node 是 VS Code 内嵌 v24.21.0。

- 每个项目、版本、seed 的 JSON 保存结构化搜索和重放结果。
- `*-CONTRACT.txt` 保存 fast-check 原生 formatter 的初始搜索报告及属性断言栈；附加计数/调用帧在 JSON 的 evidence 中。它们来自独立通用模型的观测，不是 fast-check 自动理解源码。
- `run-01` 为首轮完整对照，原生文本来自最小反例的重放，所以文本中的 Shrunk 0 与初次搜索的缩减计数不同。`run-02` 改为用官方原生 formatter 直接格式化初次搜索结果；搜索模型、种子与原型均未改变。
- 源模块、运行依赖和原型均保留原始版本。本实验不是用户研究，没有独立外部语义审查，也不能用于估计一般检测准确率或论文录用概率。

方法依据：[fast-check Properties](https://fast-check.dev/docs/core-blocks/properties/)、[Runners](https://fast-check.dev/docs/core-blocks/runners/)、[Configuration](https://fast-check.dev/docs/configuration/)。
