# Read-only code-review evidence pilot

Question: can execution evidence help an LLM judge whether a code change introduces a callback-contract violation and identify a supporting witness? This is a small model-based proxy, not a human developer study.

## Fixed design before task completions

- Six review tasks from three previously inspected real upstream pairs: eventemitter3, p-memoize and historical memoize-one; include both forward and reversed changes. Directions are correlated tasks, not six independent projects. Names/commit messages and ground-truth labels are withheld, but source symbols remain; training-data familiarity is uncontrolled.
- The common prompt includes the exact bounded contract, permitted scenario domain, numbered original sources, unified diff and ordinary sequential smoke observations. No edit or execution task is assigned.
- A: common prompt only. B: A plus unmodified native fast-check reports and neutral raw paired observations. C: B plus a deterministic observation/source/diff index. C adds no new test result or verdict. Thus A→B measures extra testing evidence; B→C examines redundant organization, not detection power.
- Derive truth from the existing independently authored runtime checks and actual paired executions, never from evaluator answers. Distinguish newly introduced failures from residual failures. Eventemitter3's historical forward fix still violates the two-once-listener case; do not label it globally safe.
- Evaluated model: the user's existing CLI-configured gpt-6.1-sol at low reasoning effort, held fixed. Calls are prompt-only model measurements through codex exec, not delegated coding agents. Fresh ephemeral empty working directory per call, no conversation history, no tools, browser, connectors, repository exploration or external lookup. A call containing tool execution is invalidated, not silently accepted. Preserve request, raw events, answer, reported usage, errors and model/config provenance. No human response-time or independent-review claim.
- One completion per arm containing all six tasks; repeat once with reversed task order, giving six fresh model calls and 36 task responses if transport succeeds. All arms within a replicate receive identical task ordering. These are repeats, not seeded deterministic sampling; temperature/model seed control is not claimed.
- Required output: two decisions (new violation introduced? any after-version violation in the stated finite domain?), one supporting scenario's counts/outcomes, source/evidence references, and a short causal explanation. Uncertain is allowed and scored separately.
- Primary deterministic measures: exact decision pair, exact observable witness, valid citation references, and missing/uncertain outputs. A valid citation is not automatically a correct causal explanation. Retain raw explanations for manual inspection; do not claim understanding improvement from citation syntax alone. No significance tests or general efficacy percentages from this tiny correlated sample.
- Avoid verdict leakage: the organized index cannot contain expected review answers or labels such as safe/fixed/bug. Both evidence arms receive exactly the same native test report and raw observations; the index only repeats/references facts and source lines already provided.
- No model/effort/prompt tuning after task answers. Do not rerun inconvenient outcomes. Transport failures remain failures, and do not become evidence of tool benefit.

Stop after this two-repeat pilot. Ceiling effects, null differences and regressions are valid outcomes. Original source modules, probe engine, static analyzer and previous experiments remain unchanged.
