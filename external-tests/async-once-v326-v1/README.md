## 这个案例为什么简单

原版核心逻辑：

```js
if (fn === null) return;
var callFn = fn;
fn = null;
callFn.apply(this, args);
```

入口绑定 fn 先保存到 callFn，随后清空 fn，再用 callFn 调用。同步重入会看到 fn 已为 null，直接返回；局部 callFn 仍持有本次实际要调用的函数。

人工变体只交换最后两句，不修改其他代码：

```js
if (fn === null) return;
var callFn = fn;
callFn.apply(this, args);
fn = null;
```

回调同步重入时 fn 仍未清空，所以会再执行一次。见证中的重入只发生一次，避免无限递归。微任务重入与普通顺序调用在两份源码中都只执行一次，显示出同步调用次序的影响。

这是明确的研究者构造变体，**不是上游真实缺陷、历史修复或维护者确认的问题**；失败的 1 项检查不算一个独立开源缺陷发现。

## 0.6.4 的覆盖缺口

当前候选外部调用主要绑定到参数名本身；这里的实际调用目标是本次入口中新建的 callFn，需要追踪“外层参数 → 局部函数值快照 → 调用”。同时要区分快照之后清空原绑定，不应误认为 callFn 也失效。当前特定单次包装器分支规则针对正向裸标识符 guard，也不覆盖 `fn === null` 的早退形式。

所以，仅放宽名字匹配或忽略参数改写不够：后续支持需要保持调用点之前的函数值来源，并验证别名没有被覆盖、重影或在分支中不确定赋值。0.6.4 检查轮仅测试；0.6.5 的受限实现见本文顶部。
