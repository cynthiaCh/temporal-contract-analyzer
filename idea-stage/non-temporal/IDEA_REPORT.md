# 非时序程序理解工具：发散候选与投入建议

日期：2026-10-31，Asia/Shanghai。接续用户“其他方向呢？除了时序的，充分调动你的思路”。本轮扩展到整个程序理解领域，不以现有 analyzer 的规则或界面作为选题边界。

状态：24 个候选提案、12 个视角；全部尚未实现或开展效用实验。两个生成槽和独立上下文排序评审均为 OpenAI 模型家族，意见只作为 provisional。初步相关工作搜索不能代替功能级查新或投稿判断。

## 怎样选：研究空间、短原型与业务场景分别判断

最终评审的综合机会排序是 N10 → N9 → N6 → N1 → N11 → N3 → N2 → N12 → N8 → N5 → N4 → N7。这是定性意见，不是量化成功概率。

- 想建立较长的科研工具线：优先看 N10 指标分母地图；N6 功能组合见证是另一个机制不同的大胆选择。
- 想先验证清楚的短原型：N9 聚合贡献解释、N1 数值特殊值、N11-A 构建缺席解释。评审建议先用 1–2 天核查 N9 与现有数据库溯源工具的实际差别。
- 更关心业务系统维护：N3 跨入口规则对照很值得考察，但取得同义输入映射与合法例外是主要成本。
- 更关心迅速交付一个可操作的工程工具：N2 配置反事实较易收窄；仍需证明现有解析日志/配置导航没有同样清楚地回答目标问题。

完整原始评审见 [ranking-review.md](ranking-review.md)。综合排名高不等于最先施工；不能在尚无真实案例时同时开发几条工具线。

## Task 1：先把选题空间打开

最有价值的切口通常是一个具体的理解问题：同一输入为什么在不同入口得到不同决策；一个数字的单位与特殊值含义如何改变；一个百分比究竟把哪些记录算进去了。下面的例子均为说明工具机制而构造，不是本轮发现的真实缺陷。

| 视角 | 可以构建的工具 | 开发者问题 | 最小可见产物 | 单人窄原型估计 |
|---|---|---|---|---|
| N1 数值语义 | 数值含义护照 | -1 表示“不限”，为什么换算后成了普通负数？ | 单位、特殊值分支和首次含义变化路径 | 6–9 天 |
| N2 配置与实现 | 配置反事实解释 | YAML 选 exact，实际为什么执行 approximate？ | 覆盖来源→最终配置→实际类，以及重解析验证的切换方案 | 5–8 天 |
| N3 跨入口规则 | 业务行为地图 / RuleMirror | 同一数据在 REST、CLI、批量导入中何处产生分歧？ | 输入域分区、各入口结果向量和具体差异输入 | 8–12 天 |
| N4 断言理解 | 断言观察地图 | 测试全绿，究竟排除了哪些替代行为？ | 仍能通过的具体错误/差异结果与断言位置 | 5–8 天 |
| N5 错误解释 | 失败信息折叠图 | 正常空值、解析错误和读取失败在哪里变成同一种返回值？ | 原因路径、合并点、所选观察边界下的可区分性 | 5–10 天 |
| N6 功能组合 | 最小组合见证 | 哪两个插件一起改变了数据或破坏了字段约束？ | 最小触发集合、并列解释和字段来源 | 8–12 天 |
| N7 契约消费 | 字段四方会诊 | Schema、接口、mock、消费代码怎样解释同一个零值？ | 同一响应见证的跨层行为矩阵 | 6–10 天 |
| N8 代码假设 | 决策余量审查 / 补丁前提审查 | 哪个决定是需求规定的？哪个转换只对部分输入成立？ | 明确约束、实现选择、碰撞或替代输出见证 | 8–12 天 |
| N9 查询含义 | 聚合单位透视 | 结果行数没变，为什么订单金额重复贡献？ | 每个原始实体的贡献次数与可复原聚合公式 | 7–10 天 |
| N10 科研代码 | 指标分母地图 / DenominatorLens | 两个比例用的是同一批样本、同一种权重吗？ | 分子、分母、成员集合、权重、筛选 cell | 9–12 天 |
| N11 构建理解 | 构建缺席解释 / 实现选择追踪 | 源码符号为什么没进产物？同一个 import 实际选了谁？ | 源码→编译/解析条件→对象/产物的有据解释 | 6–12 天 |
| N12 相似实现 | 修复适用性导航 | 相似代码哪些应同步修复，哪些有合法不同前提？ | 可重现同类差异、适用域排除、未知三类结果 | 8–12 天 |

工期仅包含指定单语言/单框架的受限工程原型，不包含真实案例搜集、完整查新、正式参与者研究、论文和公开发行。它们不是完整通用产品的一两周报价。

### 保留不同机制，不只按名字去重

两个生成槽各覆盖 N1–N12，各 12 项，共 24 项。相同视角下也有必须保留的不同机制：

- N6：Astra 从可观察输出出发求最小功能组合；Sol 从明确的字段约束出发求最小违例组合。输出变化不必然违反约束。
- N8：Astra 对实际代码决定检查显式约束是否蕴含；Sol 对新引入的已知有损操作检查其成立前提。两者不是一套方法，不应合写成“通用 AI 假设检测器”。
- N11：Astra 解释 C/C++ 符号为什么缺席；Sol 解释 JavaScript 条件导出选中了哪份实现。输入材料、分析器和交付对象不同。
- N3：跨入口分歧地图与相对确认规则的违例检查可以组合展示，但后者需要额外的规范权威，不能从前者自动推出。
- N4：在结果空间展示断言不能区分的输出，与在实现变体中寻找测试仍接受的行为，均需保证见证在声明范围内可行。

原始提案：[Astra](generator-astra.md)、[Sol](generator-sol.md)。没有因近邻工作存在而在生成阶段删除候选。

## Task 2：几个值得认真展开的方向

### A. RuleMirror：让分散在不同入口的规则变得可比较

方法：

1. 维护者选定几个入口，确认输入字段对应关系、有效输入域，以及哪些角色/对象属于同一比较情境。
2. 工具抽取受支持的纯比较与布尔条件，保留源码位置；在有限整数、枚举或受限表达式模型上比较入口结果。
3. 对每个分歧区域给一个小输入，并排回放各入口；有意不同的适用范围单独展示。

假设三个入口的资格条件分别是 `amount >= 100`、`amount > 100`、`amount >= 100 && eligible`。一个好演示是点击 `amount=100, eligible=true`，直接看到哪个入口拒绝，以及拒绝来自哪条条件。进一步点击 `eligible=false`，比较“阈值差异”和“额外资格限制”两个不同区域。

潜在理解贡献是把分散代码组织成“共同输入空间及结果分区”。核心评价应测维护者是否更准确地识别分歧及其适用范围，不把“不同”自动判成 bug。

直接近邻包括 [SIRNA, FMCAD 2026](https://arxiv.org/abs/2608.00396) 的业务规则 NL/实现一致性，以及 [SymDiff](https://www.microsoft.com/en-us/research/project/symdiff-differential-program-verifier/) 的程序关系验证。多入口理解视图是否提供实质新增价值仍待功能级比较，不能声称首次检查规则一致性。

最便宜的判断：先选 6 组三入口小程序，人工先列有限真值表，必须同时包含同适用域的意外差异、合法例外和不同写法的等价实现。若需要为每个入口重新手写答案才能完成对应，或工具强行统一不同角色的规则，则建模成本已吃掉收益。

短原型可限定三个无外部状态的 Python 函数；真实业务子系统的输入转换、权限和外部状态使它更接近 1–2 个月的研究。

### B. 数值含义护照：把特殊值与普通数值分开理解

方法：

1. 开发者声明某个字段的单位、有效范围与特殊值，例如 `quota_kib=-1` 表示不限；这些含义不能只靠字段名推断。
2. 沿有限的线性换算、比较和过滤保留“普通值分支”和“特殊值分支”，记录真实运算和源码位置。
3. 给首次发生含义不一致的路径一个输入见证。

三分钟演示可以是：

```text
输入：quota_kib = -1，已声明含义为“不限”
换算：bytes = quota_kib * 1024  → -1024
检查：bytes == -1             → false
输出：进入普通容量分支
```

另展示普通零值、正常正数和正确保留特殊值的实现，证明工具不是在看到负数时一律报警。科学计算中也可用“缺测哨兵先被换算，再参与平均数”的同类例子。

[Units Checker](https://checker-framework.org/manual/#units-checker) 等工具早已提供单位检查；潜在切口是已有未采用单位类型的代码里，单位变换与特殊值解释共同形成的可回放路径。是否超出抽象解释/精化类型已有能力仍未查清。第一版可做 Python 整数、线性变换与条件分支，约 6–9 天。

便宜判断：混合 4 个错误换算特殊值的例子和 4 个明确保留或禁止特殊值的负例。若不能解释有效零值为什么保留、特殊值为何进入普通分支，就没有证明这份解释材料有用。

### C. DenominatorLens：从论文数字回到统计对象

方法：

1. 作者选定两个输出值，提供 notebook、完整原始结果表、稳定样本 ID，以及要比较的对象单位。
2. 对受支持的筛选、合并、去重、分组和比例计算，记录成员集合、分子分母与贡献权重，并绑定 cell。
3. 展示两项结果的成员与权重差异。只有原始数据和用户选择的计分口径足够明确时，才重算共同口径；不能给缺失试验补分。

最直观的演示：

```text
A：72 / 80 = 90%，分母只含成功完成的运行
B：85 / 100 = 85%，分母含全部运行
```

再给一个更难的例子：两个分母都是 100，但各自使用不同的样本 ID。这样工具必须追成员和权重，单纯打印样本数不够。

[noWorkflow](https://github.com/gems-uff/noworkflow) 和 [Vizier](https://www.cs.uic.edu/~bglavic/dbgroup/assets/pdfpubls/BB19.pdf) 已有脚本/notebook 溯源与数据调试。候选差异是以正在被比较的指标为解释单位，直接回答纳入对象与聚合粒度问题，省去读者手工检查整张溯源图的工作。这是待验证的工作流贡献，不是首次做数据 provenance。

先做 6–8 本小 notebook：不同分母、相同数量但不同成员、同一任务多个 seed、重复连接权重、宏平均与总体比例，以及仅行序不同但口径相同的负例。若只追到输入文件，恢复不了成员与权重，则当前机制不够。若身份键、失败计分或采样单位未声明，输出未知；不能从代码自动证明统计独立性、可比性或研究诚信。

9–12 天仅适合限定 pandas 操作和比例指标；多表、多任务、多次采样及真实论文输出链值得 1–2 个月探索。

### D. 配置反事实：从“改了没作用”到可验证的实现切换

给定实际启动命令，记录配置合并/插值的真实结果，连接到实际选中的类或函数；在允许改动的配置层内寻找能真正切换实现的少量改动，并重解析确认。

演示：YAML 的 `backend=cuda` 被 CLI 的 `backend=cpu` 覆盖；改 YAML 不生效，而指定一条修改后的命令确实选择另一类。它与“配置文件跳转”相比多回答了有效选择与切换问题。

[Hydra 的维护者讨论](https://github.com/hydra-ecosystem/hydra/issues/2991) 已记录社区导航能力；[ConfProf](https://software-lab.org/publications/icpe2021.pdf) 已分析配置效果。第一版仅做 Hydra 的纯配置、显式注册表和一个选择点，约 5–8 天。必须核查现有解析日志/IDE 是否已足够回答问题，不能人为制造繁琐流程。

### E. 更大胆的组合见证：两个局部正确功能为何合起来变了

固定一份输入与一项观察量/明确不变量，执行小规模功能组合，找出导致变化或违例的最小集合，并给受影响记录的来源路径。示例是 trim 与 dedup 各自不减少两行，两者一起让两行合并；另一个例子是脱敏插件和重新读取原对象的导出插件共同破坏输出约束。

第一版固定 3–6 个确定性数据插件，可以穷举核对所有最小集合。扩大到真实插件系统时，组合爆炸、合法组合和多解是关键困难。功能交互分析早有成熟研究；值得检验的是“具体输出/字段见证”是否使定位任务更容易，而不是重新命名组合测试。小原型约 8–12 天，较大系统约 1–2 个月。

### F. 聚合贡献解释：结果行数没变，数值为何多了

输入一条 SQL、可重放小表和用户确认的原始实体键。为受支持的 JOIN/FILTER/GROUP/AGGREGATE 跟踪实体贡献权重，把最终数值展开为具体记录与算式，并指回 SQL 位置。

例如两个订单金额 100、200，各连接到 1、3 条明细，查询得到平均值 175。工具拟显示 `(100×1 + 200×3) / 4 = 175`。如果用户确认要按订单等权，才展示 `(100+200)/2 = 150` 的对照；按明细加权本身也可能完全正确。

第一版限定单个数据库、内连接、非 NULL 数值及 SUM/AVG，约 7–10 天。用 8 条能手算的微查询核对解释是否精确复原结果，包含一对多重复贡献、一对一关系及明确合法加权。公式不匹配或把合法权重一律判错，就停止扩展。

[GProM](https://github.com/IITDBGroup/gprom) 已提供 SQL provenance 和查询改写，因此先检验“把贡献压缩成开发者能直接读懂的算式与业务粒度”是否增加理解价值；不能把聚合溯源本身当作新算法。

## 其他方向为何仍保留

- N4 的“断言排除了什么”有很清楚的用户价值，但 [Oracle Gap](https://squareslab.github.io/materials/jainOracleGap.pdf) 等是直接近邻。需要展示具体可行替代行为，避免只是 mutation score 加页面。
- N5 的错误信息合流适合演示，但 [Crossing](https://pypi.org/project/crossing/) 与 [Exception Miner](https://leopoldomt.github.io/assets/pdf/2024-sbes.pdf) 已很接近。可争取的解释单位是针对指定调用者观察边界的可区分性；保留日志不等于对每个调用者都可区分，反之亦然。
- N7 可将契约允许的边界值连到消费表达式，适合具体前端/接口维护；[Specmatic](https://specmatic.io/) 已覆盖契约和 mock，需证明消费端证据链增加了什么。
- N8 不应以“再让 LLM 审查 LLM”作为机制。[AssureCode](https://arxiv.org/abs/2610.29758) 和 [CONTRA](https://arxiv.org/abs/2610.01769) 已涉及理由、假设和行为差异澄清。Sol 的有损操作碰撞见证与 Astra 的需求蕴含状态应分别验证。
- N9 可从 SQL JOIN 重复权重解释一个数值；[GProM](https://github.com/IITDBGroup/gprom) 已有成熟数据溯源。必须检验“可复原的聚合贡献解释”是否优于已有溯源查询。
- N11 的两个分支都是具体工具题目；构建记录、链接信息或实际解析器必须可获得。符号不可见、未被纳入、被回收和未知不能混成“不存在”。
- N12 必须保留合理分歧与输入域不适用的情况；代码克隆修复传播是成熟邻域，文本相似度本身不能支撑新贡献。

## Task 3：把思路变成可判断的选题

先分别验证三个问题：是否能拿到足够的真实源码与输入；是否能用相同机制解释正例和负例；是否比现有工具多回答了一个有价值的问题。此阶段不要求所有点子都跑模型或训练，也不以“找到一个反例”代替理解收益。

每个进入下一轮的方向可以先用半天至一天做纸面材料或一次性小脚本：两个真实来源、两个正确负例、一个未知/不支持例；先冻结选择规则，再看工具输出。缺真实材料时先报告不可判断。运行样例保留实际命令、输入版本和观察量，方便复核。

最低验证记录：输入与适用范围、预期可观察差异、工具输出、位置是否真实、错误解释、未知、建模时间和运行开销。如果解释主要来自研究者逐例手写答案，就应测这项成本，而非仅展示漂亮界面。

可复用现有项目的源码位置映射、报告归档或界面外壳；解析和分析机制仍需按新任务实现。选题不以“必须复用 analyzer”为前提。
