已核对的关键事实：

1. `boundary_cards.cards()` 逐条投影现有 finding；独立于 finding 的效果发现尚未实现。
2. `core.compare()` 比较 finding 的规则、作用域和证据事件签名，没有比较独立的 guard→await→effect 关系。因此提示不变并不表示时序关系不变。
3. `archive.annotate()` 已将人工意见绑定报告与 finding；`measurement.validate()` 已检查源码摘要。新增“跨版本审查”不能再以保存历史、源码指纹或拒绝过期绑定为贡献。
4. Oct29 方案已明确提出独立效果种子、有界 symbol/context 连接、effect×boundary×scenario 判断。下面 L1、L2 是该方案的实施候选。
5. AsyncG 所给 PDF 首页是 **CGO 2019**，需纠正原先 ICPC 2019 的标注。[论文](https://atlarge-research.com/pdfs/2019-nodejs-async-graphs-hsun.pdf)

以下工时是单作者完成窄实现、测试和演示的估计，不含正式参与者研究、公开发行与论文准备。所有 pilot 均为待执行方案；新颖性尚未确认。

**L1｜效果覆盖清单：让“没有卡片”仍然有可检查的入口**

- **开发者问题**：`record`、参数回调、成员写入等实际效果是否进入了审查范围？
- **构建步骤**：① 从全体事件独立提名候选效果并显示提名依据；② 每个候选列出已关联边界与断开的连接；③ 提供完整清单和过滤后的卡片，共用相同证据。
- **原计划重合**：**高，几乎就是第一优先级**。新增空间主要在“未关联候选”的产品流程，不能称为新算法。
- **相对已有工作**：可区别于 Slicito 的交互缩小分析范围：这里回答固定扫描范围中有哪些效果尚无边界证据。仅增加筛选界面不足以区别于其通用分析构件。[Slicito](https://arxiv.org/abs/2503.15675)
- **最便宜证伪 pilot**：人工标注 10 个小片段，包含参数回调、纯查询、成员写入及零 finding；比较候选清单与人工列表。若仍漏掉参数回调，或新增候选主要是无关查询，应先否定提名方案。
- **工时／风险**：4–6 天／低至中。
- **最强反对意见**：只是修复现有检测覆盖不足；覆盖提升本身未证明理解收益。
- **复用**：`core.enrich()`、两个 parser 的 references、`boundary_cards.py`、现有报告库。

**L2｜取消审查矩阵：同一次工作，不同效果的去留**

- **开发者问题**：关闭以后，已接受任务的历史记录为什么应保留，而当前界面更新为什么应停止？
- **构建步骤**：① 人工指定工作接受点及业务要求来源；② 按“接受前取消、接受后取消、重开后完成”列出情境；③ 将每个情境中的不同效果与保护分别连接，允许无法判断。
- **原计划重合**：**高，直接对应 Oct29 的 transfer 示例与逐情境设计**。可作为聚焦演示，不能换名称宣称新方向。
- **相对已有工作**：PromiseKeeper、DrAsync 关注 promise 结构、生命周期及反模式；此候选强调同一任务的不同业务效果具有不同保留要求。但这些要求必须来自仓库或开发者，工具不能推断。[PromiseKeeper](https://www.franktip.org/pubs/oopsla2018promisekeeper.pdf)、[DrAsync](https://reallytg.github.io/files/papers/drasync.pdf)
- **最便宜证伪 pilot**：两个任务、每题三个情境，比较同证据平铺材料与矩阵；检查是否减少“取消后全部丢弃”的错误，同时不增加接受时点误判。若答案主要靠额外写进矩阵的业务要求，组织方式假设未获支持。
- **工时／风险**：5–7 天／中。
- **最强反对意见**：人工输入已经包含答案；工具只提供表格。
- **复用**：`boundary_cards.py`、`archive.annotate()`、measurement 的 obligations、consumer/contrast 数据结构。

**L3｜时序关系补丁审查：提示没变，哪些关系变了？**

- **开发者问题**：把有效性检查从 `await` 前移到后，究竟改变了什么？哪个未修改调用者也需要复查？
- **构建步骤**：① 对齐两版局部声明和事件，歧义时拒绝匹配；② 比较有限的 guard／await／effect 顺序及词法控制关系；③ 用已有唯一导入调用边列出一跳未修改消费者，并明确标记“候选影响”；④ 在 diff 旁显示关系变化与源码依据。
- **原计划重合**：**中**。复用原计划的有限关系；新增点是**跨版本关系变化作为输出单元**。现有按文件／直接调用筛选与路线图的函数级定位，均不能重复计算为贡献。
- **相对已有工作**：Caprese 已推荐 JavaScript 改动影响范围；Collector-Sahab 已增强 diff 的运行差异；ChangeGuard 已比较配对执行。可争取的窄差异是：**静态、带依据的跨等待保护关系变化，并说明未修改消费者为什么需要重查**，不是泛称“语义 diff”。[Caprese](https://arxiv.org/abs/2606.21187)、[Collector-Sahab](https://arxiv.org/abs/2212.11077)、[ChangeGuard](https://arxiv.org/abs/2410.16092)
- **最便宜证伪 pilot**：8 对补丁：4 对提示数量不变但保护位置变化，4 对仅格式／无关语句变化；其中两对含未修改的直接调用者。先检查能否区分这两类，再与源码 diff 比较查找负担。如果只有专门设计的单函数例子有效，停止扩大范围。
- **工时／风险**：7–10 天／中至高。
- **最强反对意见**：有限语法 diff 没有行为保证；扩大消费者后可能退化为普通调用图影响分析。
- **复用**：`core.compare()`、events 的位置／scope／conditions、`call_links`、`archive.compare_reports()`、现有 compare 页面。
- **已有支持的范围**：根执行器提供的 synthetic 对照证明当前 compare 有缺口；它尚未证明此候选有效。

**L4｜Vue API 就绪路径：发布、可见和使用是否连接？**

- **开发者问题**：父组件调用子组件 API 时，API 是否已发布？这与组件挂载是否是同一条件？
- **构建步骤**：① 仅支持一个明确模式，例如静态子组件 import＋字面量 template ref＋`defineExpose`；② 提取 API 发布和使用锚点；③ 对齐直接组件关系，保留动态组件、别名与实例身份 unknown；④ 展示首次调用所依赖的就绪证据。
- **原计划重合**：**中**。已记录为缺口且路线图将框架语义后置；此处是具体收窄后的独立工具题目。
- **相对已有工作**：与 AsyncG／DrAsync 的运行异步图相比，审查对象是 Vue 组件间 API 发布与使用协议。仅显示组件调用图不构成差异。
- **最便宜证伪 pilot**：6 个静态父子组件组合，包括立即使用、挂载后使用、异步初始化、动态组件反例；人工核对发布与使用关系。若需要完整模板执行或响应式模型才能回答多数题目，当前范围不可行。
- **工时／风险**：10–14 天／高。
- **最强反对意见**：`mounted`、DOM 就绪和业务 API 可用不同；窄模型容易被误读为框架保证。
- **复用**：现有 Vue SFC 提取、原始位置映射、`parse.cjs`、报告 partial／unknown 表达。

**L5｜调度见证解释器：这个测试究竟证明了哪个时序情境？**

- **开发者问题**：测试通过是因为覆盖了“关闭期间完成”，还是根本没有发生该顺序？
- **构建步骤**：① 接受显式测试标记产生的少量事件记录，如 accepted、closed、resumed、effect；② 将事件映射到源码与审查情境；③ 对比两个受控调度的效果差异；④ 区分观测到的顺序、测试断言和未覆盖情境。
- **原计划重合**：**低至中**。measurement 已有 witness 容器；新增的是测试见证到情境的可检查对应。
- **相对已有工作**：NodeRacer 已通过 postponement 与 happens-before 搜索事件竞争；AsyncG 已画运行图。本候选不以调度生成或时间线为贡献，而检验“现有测试对哪个业务情境提供证据”。[NodeRacer](https://cs.au.dk/~amoeller/papers/noderacer/)
- **最便宜证伪 pilot**：手写两个 Promise gate 的微型测试，生成 4 条短轨迹；故意放入“断言通过但未跨关闭边界”的记录。若工具不能让审查者识别该空洞见证，解释器没有达到目标。
- **工时／风险**：8–12 天／中至高。
- **最强反对意见**：插桩标记和情境映射成本过高；实质上是测试日志浏览器。
- **复用**：measurement 的 `witness_artifacts`、source anchors、归档和报告页面。执行器应作为可选配套工具，与当前静态分析边界分开说明。

**L6｜审查意见失效解释：哪条旧结论需要重新检查？**

- **开发者问题**：源码变了，旧的“保护充分”意见因为什么失去适用依据？
- **构建步骤**：① 人工结论显式引用有限 evidence set，而非只写自由文本；② 对两版证据锚点及关系进行保守对齐；③ 输出“依据变化／映射不确定／暂未发现依据变化”及理由；④ 生成重新核查队列，保持旧意见原样。
- **原计划重合**：**低**；但报告归档、摘要绑定和防止旧定位误用已经存在。
- **相对已有工作**：Caprese 推荐应检查的代码，此候选定位应重查的**既有人类结论及其依赖**；区别仍需进一步检索审查意见、annotation maintenance 等相关工作，不能据现有清单宣称新颖。
- **最便宜证伪 pilot**：给 6 条人工结论各构造两版：无关格式变化、保护变化、未修改文件依赖的 API 变化。与“整个文件变化就全部失效”基线比较。若没有明显减少无关重查，细粒度依赖成本不值得。
- **工时／风险**：5–8 天／中。
- **最强反对意见**：结论真正依赖什么往往未写全；“依据未变”容易被误认为结论仍然正确。
- **复用**：`archive.annotate()`、`measurement.validate()` 的 evidence/source binding、`compare_reports()`。
- **合并关系**：与 L3 共用事件对齐，不能把两者包装成两个独立算法贡献。

**L7｜Python 清理完成审查：发起清理不等于清理完成**

- **开发者问题**：取消退出后，是调用了 `aclose()`，还是拥有的资源已经完成关闭？
- **构建步骤**：① 聚焦显式 `finally`、`async with`、`await close/aclose` 和 `shield`；② 关联清理发起、等待及可见退出位置；③ 区分资源所有权证据与名称线索；④ 以受控任务取消展示正常退出与清理被中断的不同证据。
- **原计划重合**：**中**。现有规则和限界已提出问题；新增是完成关系的窄模型及交互解释。
- **相对已有工作**：PromiseKeeper／DrAsync 的 promise 生命周期不能直接承担 Python 资源所有权与退出清理的判断；但换语言不足以成为新意，必须体现“谁负责等谁完成”的可检查关系。
- **最便宜证伪 pilot**：6 个 asyncio 片段：漏 await、显式 await、清理任务被保留但调用者取消、非所有者、异步迭代提前退出等；由可控 Event 记录是否完成。若工具仍只能报告 finally 中出现 close，候选没有超越现有规则。
- **工时／风险**：7–10 天／中至高。
- **最强反对意见**：取消语义和资源实现决定完成保证；有限语法分析很难给出足够有用的答案。
- **复用**：`python_adapter.py` 的 try/finally、resource_scope、await、return 事件与现有 Python 三类 finding。

**L8｜API 生命周期契约入门页：把使用要求连到调用点**

- **开发者问题**：第一次使用这个 API，必须先满足什么、关闭以后还能做什么、哪些消费者有例外？
- **构建步骤**：① 维护者录入一个 API 的少量明确要求并引用文档／测试版本；② 用唯一 import／直接调用定位消费者；③ 每个消费者显示所用规则、源码证据与缺失连接；④ 从违反顺序和合法例外各提供一个可导航示例。
- **原计划重合**：**低至中**。复用 requirement evidence，不扩展成自动契约挖掘。
- **相对已有工作**：相对 Slicito 的通用交互分析，目标是从维护者确认的 API 使用规则出发理解调用点。但 typestate、API protocol mining、文档生成是必须补查的直接邻域；现有相关工作不足以确认其差异。
- **最便宜证伪 pilot**：选一个真实 API、3 条要求、6 个消费者，限制维护者建模时间为一小时；让新读者回答使用／关闭／例外问题。若规则编写需要逐消费者写答案，无法扩展为工具。
- **工时／风险**：6–9 天／中。
- **最强反对意见**：维护的是另一份可能过期的文档；贡献与协议文档或 typestate 工具高度重叠。
- **复用**：import binding、`call_links`、measurement 的 requirement/evidence、报告库源码导航。

生成阶段建议：**优先对 L3 做一天以内的证伪检查，再决定是否作为唯一新增主线。**它有当前 compare 的具体缺口作为起点，能在短演示中呈现不同于卡片重排的行为；但 Caprese、Collector-Sahab、ChangeGuard 使“改动理解”这个大标题不再足够。L1/L2 更适合作为原方案的稳妥实施，不应与 L3 同时扩成三条投稿贡献。
